Summary

Participants understood the concept of adding and updating packages, but consistently struggled to initiate the flow — the entry point was too buried for first-time discovery. Once inside the deployment dialog, the language mismatch between internal version names and familiar semantic versioning caused significant hesitation.

The test largely confirmed our hypothesis that the confirmation step needs a dependency impact view before commit. All five participants paused and asked what downstream effects to expect before proceeding. The rollback path was not discovered by any participant unprompted.

Common Findings

Common Failings

  • Entry point not discoverable (Task 1). 4 of 5 participants did not find "Package Manager" on first pass — they looked in Settings, the sidebar, and the project config file before locating it. Three required a hint. The trigger was consistently labeled "unexpected."
  • Conflict resolution flow too opaque (Task 3). 4 of 5 participants could not complete Task 3. The conflict indicator appeared only in a secondary status bar area that most participants never noticed. Once seen, the path to resolution wasn't clear — no call-to-action linked the warning to the resolution UI.
  • No perceived success state after deployment. 3 of 5 participants were unsure whether their action had completed. They clicked "Deploy" and were returned to the same screen with no visible change.

Common Confusion

  • "Deploy" vs. "Install" terminology. All 5 participants hesitated at the "Deploy Package" label. Developers with npm/pip/brew backgrounds associated "deploy" with releasing code, not adding a dependency. All 5
  • Internal version names instead of semver. 4 participants expected semantic version numbers (e.g., 2.4.1) but saw internal build identifiers (e.g., auth-svc.2026.05.a). Two tried to sort by version number before understanding the format. 4 of 5
  • Confirmation step lacks context. All participants paused at the confirmation modal and asked (aloud or to the moderator) what downstream effects to expect — which packages would be affected, whether anything would break. All 5

Common Feedback

  • All participants responded positively to the version timeline component once they understood it. "I like seeing the history" came up in 4 recap sessions. 4 of 5
  • 3 participants expected a search bar in the package catalog. Two tried pressing Cmd+F. 3 of 5
  • 2 participants mentioned wanting to see a dependency graph or impact analysis before confirming. Both had ops backgrounds. 2 of 5
  • 2 participants tried using keyboard shortcuts common in IDEs (Cmd+Shift+P, Cmd+K) to navigate. Neither expected to find Package Manager that way but noted they'd try it. 2 of 5
  • All participants appreciated the ability to pin a specific version rather than always being on latest. All 5
Action Items / Next Steps
Now
Rename "Deploy Package" → "Add Package" (or "Install Package") Align terminology with developer mental models from npm/pip/brew ecosystems. Validate the new label with 2–3 developers before shipping.
Source: All 5 participants hesitated at "Deploy" label
Now
Surface conflict indicators more prominently Move conflict state out of the status bar and into the main package list. Add a clear call-to-action that links directly to resolution steps.
Source: Task 3 — 4 of 5 failed to notice or resolve conflict
Now
Add a success state after deployment Show a visible confirmation (toast, status update, or inline badge) after a package is installed or updated. The current flow returns to the same screen silently.
Source: 3 participants unsure if deployment completed
Soon
Show semver-equivalent version labels alongside internal identifiers Display friendly version numbers (e.g., 2.4.1) paired with build identifiers, or map them so developers can orient to familiar conventions.
Source: 4 participants couldn't parse internal version format
Soon
Add dependency impact summary to the confirmation step Before the user confirms a deployment, show which other packages will be affected. Even a simple list ("3 packages will be updated") reduces uncertainty significantly.
Source: All 5 paused at confirmation and asked about downstream effects
Soon
Improve Package Manager entry point discoverability Consider adding a project-level shortcut, a command palette entry, or a contextual link from the code editor. Current placement requires prior knowledge to find.
Source: Task 1 — 4 of 5 failed first-pass discovery
Later
Add search to the package catalog Low-effort, high-expected feature. Three participants reached for Cmd+F.
Source: 3 participants tried to search without finding a search bar
Later
Investigate rollback discoverability Zero participants found the rollback path unprompted. Worth a dedicated follow-up study or a targeted design iteration before this feature ships.
Source: Rollback — 0 of 5 discovered unprompted
